# v0.10.0 reference numbers

Measured on 2026-11-06 with the procedure of `dev/mcapbench/bench_compare.py`: the
function-level benches built onto the `v0.10.0` tag (commit `325b2f3`), three rounds
interleaved with v0.6.0–v0.9.0 and the then-current `main`. That run predates the
per-round rotation and used the same order every round, oldest release first.

These numbers are for orientation only: the order of magnitude per case, and how much a
case moves between rounds. Do not compare a later run against them. The same binary
measured at another time has drifted by 5% or more, so a regression check has to rebuild
v0.10.0 and interleave it with the candidate (see [Comparing revisions](../benchmark.md#comparing-revisions)).

## Conditions

- AMD Ryzen 7 5800X (8 cores / 16 threads), Linux x86_64, CPU governor `performance`.
- Rust 1.99.1, `bench` profile, `RAYON_NUM_THREADS=8`, fixtures on tmpfs.
- Shared host (load average 2–5), no CPU pinning.
- Criterion settings from `mcapbench::criterion()`: 10 samples, 1 s warm-up, 3 s measurement.

The two `Bytes` cases are dominated by copying a 1 MiB payload and vary too much between
rounds to show a regression.

Older releases were measured in the same run and are not kept: v0.6.0 to v0.9.0 stayed
within round-to-round noise of each other, and v0.10.0 was as fast or faster in every case.

\* Multi-topic cases were measured separately on 2026-11-07 using the `reader_multi` suite against v0.10.0

conditions above. The table shows the median and range of three consecutive Criterion
point estimates. These runs were not interleaved with another revision. Like the reference numbers
above, they are for orientation and cannot establish a performance regression.
