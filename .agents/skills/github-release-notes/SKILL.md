# GitHub release notes

Inspect the target release and several recent manually written releases to learn their structure, language, level of detail, and links. Identify the preceding release tag and examine the commits, relevant PR descriptions, and code changes between the tags; do not rely on autogenerated titles alone. Include user-visible additions, fixes, breaking changes and performance improvements as appropriate, with accurate limitations and migration guidance. Omit internal refactors unless relevant to users.

For this repository, use [the release note format](references/format.md); omit sections without relevant changes. Follow the repository's established headings, component grouping, introductory text, PR links, and full changelog link. Preserve the release title, tag, assets, and other metadata unless requested otherwise. Write a complete body to a temporary file and review it against the changes. Before any GitHub release update, show the user the target release and the complete proposed body, ask for explicit approval, and wait for their response. Proceed only after approval; if the user requests changes, revise the proposal and obtain approval for the revised body. For draft-only requests, present the draft without updating the release. Use an available GitHub integration or `gh release edit <tag> --notes-file <file>`, then read back the release body to verify it. Never push git changes as part of this task unless explicitly requested.
